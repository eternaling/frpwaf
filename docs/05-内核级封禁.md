# 05 · 内核级封禁（ipset + iptables）

## 1. 为什么需要内核级封禁

frp 的 `httpPlugins` 是**应用层**准入：被拒绝的连接，其 **TCP 握手其实已经完成**，
由 frps 主动断开。于是被禁 IP 可以不停重连：

- 每次重连都写一条 `conn_log`，`proxy_stat` 计数持续上涨；
- 每次都触发一次 `engine.decide()`，白白消耗 frps 与 WAF 的 CPU / 连接资源；
- 攻击流量仍会打到 frps 上（只是被拒），带宽与连接数被占用。

`firewall` 模块把「黑名单 + 生效封禁」同步进一个 **ipset 集合**，并在 INPUT 链
最前面用一条规则对命中集合的来源 **DROP**。这样被禁 IP 的数据包在**内核层**即被丢弃，
连不到 frps，计数自然停止。

## 2. 内核对象

| 对象 | 名称 | 说明 |
|---|---|---|
| ipset（IPv4） | `frpwaf_block` | `hash:net`，支持 per-entry timeout |
| ipset（IPv6） | `frpwaf_block6` | `hash:net family inet6` |
| iptables 链 | `FRPWAF_BLOCK` | 由 `INPUT` 第 1 条跳入 |
| iptables 规则 | `-m set --match-set frpwaf_block src -j DROP` | 命中集合即丢包 |
| ip6tables 链 | `FRPWAF_BLOCK` | 同理，匹配 `frpwaf_block6` |
| nat 链 | `FRPWAF_REDIRECT` | nat/PREROUTING 第 1 条跳入（仅「拦截页模式」下发） |
| nat 规则 | `-m set --match-set frpwaf_block src -p tcp --dport <HTTP端口> -j REDIRECT --to-ports <block_page_port>` | 命中封禁则改道到拦截页服务 |

`_ensure_sets()` / `_ensure_drop()` / `_ensure_redirect()` 幂等地创建集合 / 链 / 规则
（`-exist` + `-C` 判存在再插/再删）。

## 3. 可用性判断（`available()`）

必须同时满足：
1. 进程 `euid == 0`（root）；
2. 系统有 `ipset`；
3. 系统有 `iptables`。

否则 `available()` 返回 `False`，`sync()` / `sync_from_store()` 直接返回 `False`，
**自动降级为「不启用内核封禁」**——此时仍由 frp 应用层拦截，只是连接计数会继续增长。
插件端「IP 名单 / 封禁」页的「内核级封禁」卡片会显示 `available=false`。

## 4. 同步逻辑（`sync` / `sync_from_store`）

### 4.1 输入

`sync_from_store()` 从数据库读取并**按开关裁剪**：

```python
def sync_from_store():
    if not available():
        return False
    with _sync_lock:
        cfg = config.get()
        mode = _mode(cfg)          # drop / redirect / off
        if mode == "off":
            _clear_drop(); _clear_redirect()
            return False
        perms = [永久黑名单 CIDR...] if cfg.get("blacklist_enabled", True) else []
        whites = [白名单 CIDR...] if cfg.get("whitelist_enabled", False) else []
        bans = store.active_bans()
        ok = sync(perms, bans, whites)        # 填充 ipset（白名单差集）
        with _lock:
            _ensure_sets()
            if mode == "drop":
                _clear_redirect(); _ensure_drop()
            else:
                ports = _redirect_ports(cfg)
                if ports:
                    _clear_drop(); _ensure_redirect(ports, cfg["block_page_port"])
                else:
                    _clear_redirect(); _ensure_drop()   # 无端口 → 退化 DROP
        return ok
```

> **Bug A 修复**：早期版本忽略 `blacklist_enabled` / `whitelist_enabled` 两个开关，
> 导致「关掉黑名单后内核仍丢包」「关掉白名单后黑名单漏封」。现按开关裁剪，
> 使**内核拦截集合 ≡ 应用层实际会拒绝的集合**。

### 4.2 组装 `want` 集合

`sync(permanent, bans, whitelist)` 构造两个字典 `want4` / `want6`
（`{member: timeout}`，`timeout<=0` 表示永久）：

1. **先放临时封禁**：`timeout = expire_at - now`；已到期（`<=0`）跳过（交给 ipset 自身超时移除）。
2. **后放永久黑名单**：`timeout = 0`，始终永久，**不被临时封禁覆盖**。
3. **白名单差集**：若白名单开启，对 `want4`/`want6` 调 `_apply_whitelist`。

### 4.3 白名单差集（Bug C，关键）

**仅「成员落在白名单内」直接删除是不够的。** 反例：

- 黑名单有 `10.0.0.0/8`（整段下发）；
- 白名单只放行 `10.0.0.5`（单个 IP）；
- 若只判断「`10.0.0.0/8` 是否在白名单内」→ 否，整段照发 → 内核把 `10.0.0.5` 也 DROP 了。
- 结果：**应用层放行（白名单优先），内核层却拦截**——用户连不上。

修复：`_apply_whitelist(bucket, wnets)` 对每个成员做 **CIDR 差集**：

```python
def _apply_whitelist(bucket, wnets):
    for m in list(bucket):
        net = ip_network(m)
        t = bucket[m]
        remaining = [net]
        for w in wnets:
            if w.version != net.version:
                continue
            newr = []
            for n in remaining:
                if not n.overlaps(w):
                    newr.append(n)              # 不相交：保留
                elif n.subnet_of(w):
                    pass                        # 整段在白名单内：丢弃
                else:
                    newr.extend(n.address_exclude(w))   # w 在 n 内：取差集
            remaining = newr
        if len(remaining) == 1 and _member(remaining[0]) == m:
            continue                            # 未变化
        bucket.pop(m, None)
        for n in remaining:
            bucket[_member(n)] = t              # 拆出的子段继承原 timeout
```

于是 `10.0.0.0/8` 会被拆成「`10.0.0.0/8` 减去 `10.0.0.5`」的若干子网下发，
`10.0.0.5` 不再进入内核集合。

- `_member(net)`：`/32`、`/128` 用裸地址，其余用 CIDR 字符串。
- 差集结果继承原成员的 `timeout`（临时封禁的子段仍会到期）。
- **该逻辑经 400 轮随机 fuzz 测试（约 12 万次随机 IP 探测）验证，0 处不一致。**

### 4.4 下发（`_reconcile`）

`_reconcile(setname, want)` 让 ipset 内容与 `want` 一致：

- 已存在且「永久/临时」性质一致 → 跳过；
- 性质变化（永久↔临时）→ 先 `del` 再 `add`；
- `want` 中有、集合中没有 → `add`（带或不带 timeout）；
- 集合中有、`want` 中没有 → `del`。

> **批量提交（本轮加固）**：为避免大批量封禁时逐条 `ipset add/del` 的进程
> 风暴，`_reconcile` 优先用 `ipset restore -exist` 把差异**一次性批量提交**
> （脚本里 `add`/`del` 混合输出）；`restore` 不可用或失败时自动退化为逐条
> 命令，行为与旧版一致。
>
> **并发串行**：快照（读名单/封禁）与下发**全程持 `_sync_lock`**，
> 后到的同步等待并重新读最新快照；引擎触发的密集同步请求由单工作线程合并，
> 避免旧快照在解封后覆盖新状态。

## 5. 三种处置模式与关闭清理（重要）

内核层处置由两个开关决定（`_mode()`）：

| 模式 | 条件 | 内核动作 | 被封 IP 看到 |
|---|---|---|---|
| `drop` | `fw_sync_enabled` 开 | 下发 DROP，清理 REDIRECT | 连接超时，**无页面**（静默） |
| `redirect` | `fw_sync_enabled` 关 + `block_page_enabled` 开 | 摘除 DROP，下发 nat REDIRECT 到拦截页服务 | 封禁页 / 风控页 |
| `off` | 两者都关 | 清理 DROP 与 REDIRECT | 连接重置，无页面 |

> **为什么 redirect 模式必须先摘 DROP**：nat/PREROUTING 在 filter/INPUT 之前，
> 但改道后的包（目的端口变成 `block_page_port`）仍会在 INPUT 命中 `FRPWAF_BLOCK`
> 的 DROP 规则（源 IP 仍在集合中），从而「刚改道就被丢弃」。故 redirect 模式先
> `_clear_drop()` 再 `_ensure_redirect()`。

**教训（历史）**：把 `fw_sync_enabled` 关掉后，如果只停止「继续同步」而不清理已下发的
规则，内核里旧的 ipset 条目 / iptables 规则**仍在丢包**，表现为「面板显示已关闭内核封禁，
却仍被拦截」。因此所有路径统一调用 `sync_from_store()`，由它按模式决定
DROP / REDIRECT / 清理——不再有「关就 teardown」的分支：

- `daemon._fw_sync()`、`/api/config` 保存、`/api/kernban/sync`。
- 插件端 `frpwaf_main._fw_sync()` / `kernban_sync()`。
- 卸载：`uninstall_waf()`、`uninstall.sh` 仍调用 `teardown()` 彻底拆除。

`teardown()` 删除 INPUT 跳转、清空并删除 `FRPWAF_BLOCK` 链、删除 nat `FRPWAF_REDIRECT`
链、销毁两个 ipset。

### 5.1 REDIRECT 目标端口（`_redirect_ports`）

- 显式配置 `block_page_redirect_ports`（逗号分隔，如 `"80,8080"`）优先；
- 留空则自动读取 frps 配置的 `vhostHTTPPort`（`frp.load_config("frps")`）；
- 都取不到 → 退化为 DROP（至少保证拦截）。

规则幂等：先 `iptables -t nat -C` 判存在，不存在才 `-A`。IPv6 走 `ip6tables -t nat`。
拦截页服务本身见 `app/blockpage.py` 与 [04 §3.7.1](04-数据模型与配置项.md)。

## 6. 后台对账与解封

- `daemon._bg_loop()` 每 10 秒调 `_fw_sync()`，把当前名单/封禁**对账**到内核
  （即使某次同步失败，10 秒后会自愈）。
- 解封：`/api/bans` 的 `unban` 会先 `store.unban_ip()` 再 `firewall.remove(ip)`
  再 `_fw_sync()`，立即从内核移除。
- 封禁到期：后台 `engine.auto_release()` 释放，下一次 `_fw_sync()` 时集合中
  已到期的临时条目也会因 `timeout` 归零由 ipset 自行移除。

## 7. 状态查询（`status()`）

返回：

```json
{
  "available": true,          // 是否支持（root + ipset + iptables）
  "enabled": true,            // 处置模式 != off
  "mode": "drop",             // drop / redirect / off
  "set4": 4,                  // frpwaf_block 条目数
  "set6": 0,                  // frpwaf_block6 条目数
  "rule": true,               // INPUT 是否已挂 FRPWAF_BLOCK
  "redirect": false,          // nat/PREROUTING 是否已挂 FRPWAF_REDIRECT
  "redirect_ports": [18080]   // 当前 REDIRECT 目标端口
}
```

> `status()` 填 `available/mode/enabled/set4/set6/rule/redirect/redirect_ports`；
> `/api/kernban` 与插件端 `kernban_status` 仍会覆盖 `enabled` 为当前 `fw_sync_enabled`
> （表示「内核丢包封禁」开关本身），并在 UI 上结合 `mode` 展示实际处置。

在宝塔插件端「**IP 名单 / 封禁**」页的「内核级封禁」卡片（含状态与「立即同步」按钮）
可手动触发 `kernban_sync`；独立 Web 端自 2026-10 起也提供「**内核封禁**」页
（状态 + 「立即同步」，二次确认 + 审计）。也可直接调用 `/api/kernban/sync`。

### 7.1 其它工具函数

| 函数 | 作用 |
|---|---|
| `remove(ip)` | 从内核集合移除单个 IP/CIDR（解封时调用；`ipset del -exist`） |
| `flush()` | 清空集合内所有条目（**保留**集合与 iptables 规则） |
| `teardown()` | 删除 iptables 规则/链与两个 ipset（关闭开关、卸载时调用） |

> `flush()` 与 `teardown()` 的区别：前者只清条目（规则仍在，集合仍在），
> 后者彻底拆除（下次 `sync` 会重新 `_ensure()` 建好）。关闭 `fw_sync_enabled` 走
> **`teardown()`**（彻底拆除，避免残留规则继续丢包）。

### 7.2 谁在调用同步

| 调用方 | 时机 |
|---|---|
| `daemon._bg_loop()` | 每 10 秒对账一次（兜底自愈） |
| `daemon` `/api/config`、`/api/kernban/sync` | 策略保存 / 手动同步（关闭态触发 `teardown`） |
| `daemon` `/api/bans`、`/api/iplist` | 封禁/解封/名单变更后立即触发（异步合并，不阻塞响应） |
| `engine` 第 5/6 步命中封禁 | 触发一次异步同步（事件去重，同一时刻只跑一个） |
| 插件端 `frpwaf_main._fw_sync()` / `kernban_sync()` | 插件页操作与手动同步 |

## 8. 常见问题

| 现象 | 原因 / 处置 |
|---|---|
| `available=false` | 非 root / 缺 ipset 或 iptables。装 `ipset`、用 root 运行守护进程 |
| 关闭内核封禁后仍被拦 | 旧版本未清理残留；升级到含 Bug A 修复的版本，或手动 `kernban_sync`（关闭态会清理） |
| 被封 IP 看不到拦截页 | 检查 `block_page_enabled` 是否开、`block_page_port` 是否监听、`block_page_redirect_ports`/frps `vhostHTTPPort` 是否正确；HTTPS(TLS) 端口无法展示可读页面（退化为 DROP） |
| 白名单 IP 连不上 | 升级到含 Bug C 修复的版本（CIDR 差集）；确认白名单开关已开 |
| 内核集合条目数对不上 | 正常：白名单差集会拆分 CIDR；每 10 秒对账 |
| IPv6 未生效 | 需系统有 `ip6tables`；`frpwaf_block6` 才创建 |
