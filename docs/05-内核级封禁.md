# 05 · 内核级封禁（ipset + iptables）

## 1. 为什么需要内核级封禁

frp 的 `httpPlugins` 是**应用层**准入：被拒绝的连接，其 **TCP 握手其实已经完成**，
由 frps 主动断开。于是被禁 IP 可以不停重连：

- 每次重连都写一条 `conn_log`，`proxy_stat` 计数持续上涨；
- 每次都触发一次 `engine.decide()`，白白消耗 frps 与 WAF 的 CPU / 连接资源；
- 攻击流量仍会打到 frps 上（只是被拒），带宽与连接数被占用。

`firewall` 模块把「黑名单 + 生效封禁」同步进一个 **ipset 集合**，并在 INPUT 链
最前面用一条规则对命中集合的来源 **DROP**。这样被禁 IP 的数据包在**内核层**即被丢弃，
连不到 frps，计数自然停止。

## 2. 内核对象

| 对象 | 名称 | 说明 |
|---|---|---|
| ipset（IPv4） | `frpwaf_block` | `hash:net`，支持 per-entry timeout |
| ipset（IPv6） | `frpwaf_block6` | `hash:net family inet6` |
| iptables 链 | `FRPWAF_BLOCK` | 由 `INPUT` 第 1 条跳入 |
| iptables 规则 | `-m set --match-set frpwaf_block src -j DROP` | 命中集合即丢包 |
| ip6tables 链 | `FRPWAF_BLOCK` | 同理，匹配 `frpwaf_block6` |
| nat 链 | `FRPWAF_REDIRECT` | nat/PREROUTING 第 1 条跳入（仅「拦截页模式」下发） |
| nat 规则 | `-m set --match-set frpwaf_block src -p tcp --dport <HTTP端口> -j REDIRECT --to-ports <block_page_port>` | 命中封禁则改道到拦截页服务 |

`_ensure_sets()` / `_ensure_drop()` / `_ensure_redirect()` 幂等地创建集合 / 链 / 规则
（`-exist` + `-C` 判存在再插/再删）。

## 3. 可用性判断（`available()`）

必须同时满足：
1. 进程 `euid == 0`（root）；
2. 系统有 `ipset`；
3. 系统有 `iptables`。

否则 `available()` 返回 `False`，`sync()` / `sync_from_store()` 直接返回 `False`，
**自动降级为「不启用内核封禁」**——此时仍由 frp 应用层拦截，只是连接计数会继续增长。
插件端「IP 名单 / 封禁」页的「内核级封禁」卡片会显示 `available=false`。

## 4. 同步逻辑（`sync` / `sync_from_store`）

### 4.1 输入与主流程

`sync_from_store()` 从数据库读取并**按开关裁剪**，然后交给两层「记忆化」下发
（规则层 `_apply_rules`、成员层 `_sync_sets` → `_reconcile`）：

```python
def sync_from_store():
    if not available():
        return False
    from . import config, store
    with _sync_lock:                      # 快照构建与下发全程互斥
        cfg = config.get()
        mode = _mode(cfg)                 # drop / redirect / off
        block_port = int(cfg.get("block_page_port") or 7081)
        if mode == "off":
            with _lock:
                _apply_rules("off", (), 0)     # 记忆化：形态没变就 0 fork
            return False
        ports = ()
        shape = "drop"
        if mode == "redirect":
            ports = tuple(_redirect_ports(cfg))
            shape = "redirect" if ports else "drop"   # 无目标端口 → 退化为 DROP
        perms = []
        if cfg.get("blacklist_enabled", True):
            perms = [r["cidr"] for r in store._query(
                "SELECT cidr FROM ip_list WHERE list_type='black'")]
        whites = []
        if cfg.get("whitelist_enabled", False):
            whites = [r["cidr"] for r in store._query(
                "SELECT cidr FROM ip_list WHERE list_type='white'")]
        bans = store.active_bans()        # 临时封禁不受名单开关影响
        want4, want6 = _build_want(perms, bans, whites)   # 内部做白名单差集
        ok = True
        with _lock:
            ok = _sync_sets(want4, want6)                  # 集合存在 + 成员差量
            ok = _apply_rules(shape, ports, block_port) and ok   # 规则形态
        return ok
```

与早期实现的区别：不再每轮无条件执行 `_ensure_sets()` / `_clear_redirect()` /
`_ensure_drop()`，而是把「本进程已经下发过什么」记在内存里（`_RULES` / `_MEMBERS` /
`_sets_ok`），只有**配置变化、下发失败或审计到期**时才真正 fork 命令。
详见 §4.5。

> **Bug A 修复（仍然有效）**：早期版本忽略 `blacklist_enabled` / `whitelist_enabled` 两个开关，
> 导致「关掉黑名单后内核仍丢包」「关掉白名单后黑名单漏封」。现按开关裁剪，
> 使**内核拦截集合 ≡ 应用层实际会拒绝的集合**。

### 4.2 组装 `want` 集合

`_build_want(permanent, bans, whitelist)` 构造两个字典 `want4` / `want6`
（**`{member: 绝对到期时间戳}`**，`0` 表示永久）：

1. **先放临时封禁**：值为 `expire_at`（绝对时间）；已到期（`<= now`）跳过
   （交给集合自身的 per-entry timeout 移除）。
2. **后放永久黑名单**：值为 `0`，始终永久，**不被临时封禁覆盖**。
3. **白名单差集**：若白名单开启，对 `want4`/`want6` 调 `_apply_whitelist`。

> 为什么用**绝对到期时刻**而不是剩余秒数：记忆化要能把「本次目标」与「上次已下发」
> 直接比大小，而不必每轮重算。内核真值（`ipset save` 给出的是**剩余** timeout）会被
> `_abs_deadlines()` 转换成绝对时间戳后再比。

### 4.3 白名单差集（Bug C，关键）

**仅「成员落在白名单内」直接删除是不够的。** 反例：

- 黑名单有 `10.0.0.0/8`（整段下发）；
- 白名单只放行 `10.0.0.5`（单个 IP）；
- 若只判断「`10.0.0.0/8` 是否在白名单内」→ 否，整段照发 → 内核把 `10.0.0.5` 也 DROP 了。
- 结果：**应用层放行（白名单优先），内核层却拦截**——用户连不上。

修复：`_apply_whitelist(bucket, wnets)` 对每个成员做 **CIDR 差集**：

```python
def _apply_whitelist(bucket, wnets):
    for m in list(bucket):
        net = ip_network(m)
        t = bucket[m]
        remaining = [net]
        for w in wnets:
            if w.version != net.version:
                continue
            newr = []
            for n in remaining:
                if not n.overlaps(w):
                    newr.append(n)              # 不相交：保留
                elif n.subnet_of(w):
                    pass                        # 整段在白名单内：丢弃
                else:
                    newr.extend(n.address_exclude(w))   # w 在 n 内：取差集
            remaining = newr
        if len(remaining) == 1 and _member(remaining[0]) == m:
            continue                            # 未变化
        bucket.pop(m, None)
        for n in remaining:
            bucket[_member(n)] = t              # 拆出的子段继承原 timeout
```

于是 `10.0.0.0/8` 会被拆成「`10.0.0.0/8` 减去 `10.0.0.5`」的若干子网下发，
`10.0.0.5` 不再进入内核集合。

- `_member(net)`：`/32`、`/128` 用裸地址，其余用 CIDR 字符串。
- 差集结果继承原成员的 `timeout`（临时封禁的子段仍会到期）。
- **该逻辑经 400 轮随机 fuzz 测试（约 12 万次随机 IP 探测）验证，0 处不一致。**

### 4.4 下发（`_reconcile`）

`_reconcile(setname, want, cur=None)` 让 ipset 内容与 `want` 一致，**只下发差量**：

| 情形 | 动作 |
|---|---|
| `want` 有、基线没有 | `add`（带或不带 timeout） |
| 两边都有，且「永久/临时」性质一致、到期时刻在容差内 | 跳过（不 fork） |
| 两边都有，但性质变化（永久↔临时） | `del` + `add` |
| 两边都有，且到期时刻变了 | `del` + `add`（见下方 timeout 刷新） |
| 基线有、`want` 没有，且未到期 | `del` |
| 基线有、`want` 没有，但已过期 | 跳过（集合自身 per-entry timeout 会移除） |

**基线（`base`）从哪来**：

1. 审计轮（`_sync_sets` 传入 `cur`）：`ipset save` 的剩余 timeout → `_abs_deadlines()` 转绝对时刻；
2. 否则用进程内记忆 `_MEMBERS[setname]`；
3. 记忆为「未知」（首次同步 / 上次下发失败）→ 读一次内核真值（`ipset save`）再比。

> **临时封禁延长会刷新 timeout（P2-3 修复）**：`ipset add -exist` 对**已存在**条目
> **不会**刷新 timeout，旧实现因此会让「封禁被延长」的 IP 按**旧到期时间提前解封**
> （应用层还在拦，但内核层已经不丢包，等于白开了内核封禁）。现在只要新旧到期时刻
> 相差超过 **10% 且至少 5 秒**（`TIMEOUT_REFRESH_RATIO` / `TIMEOUT_REFRESH_MIN`），
> 就 `del` + `add` 重建该条目；容差是为了避开后台轮询造成的小抖动，避免每次都重建。

> **批量提交**：为避免大批量封禁时逐条 `ipset add/del` 的进程风暴，差异用
> `ipset restore -exist` **一次性批量提交**；`restore` 不可用或失败时自动退化为逐条命令。
> **并发串行**：快照（读名单/封禁）与下发**全程持 `_sync_lock`**，后到的同步等待并
> 重新读最新快照，避免旧快照在解封后覆盖新状态。

### 4.5 状态记忆化与周期审计（稳态 0 fork）

历史问题：后台每 10 秒无条件执行 `_ensure_sets`（2 次 `ipset create`）、
`_clear_redirect`（**drop 模式下 6 条 `iptables -D` 按设计必然失败**）、
`_ensure_drop`、`ipset save` ——稳态下一轮约 **18 次 `subprocess` fork**，
小规格 ECS 长期占 1%~2% 单核，并在内核日志里制造噪音（错误全被 `2>/dev/null` 吞掉，
真实故障反而看不见）。

现改为**两层记忆 + 周期审计**：

| 记忆 | 内容 | 命中效果 |
|---|---|---|
| `_RULES` | 上次成功下发的**规则形态**（`mode`=`drop`/`redirect`/`off`、REDIRECT 端口集合、拦截页端口、`checked_at`） | 形态与配置都没变 → 直接返回，**0 fork** |
| `_MEMBERS` | 每个集合**已下发的成员 + 绝对到期时间戳** | 与目标快照一致 → 不发任何命令，**0 fork** |
| `_sets_ok` | 集合已确认存在 | 省掉每轮 2 次 `ipset create` |

**审计（`VERIFY_INTERVAL = 600` 秒）**：记忆化会失去「外部改动（`firewalld` reload、
`iptables -F`、`ipset flush`）后自动补回」的能力，所以每 10 分钟用**只读探测**核对内核真值：

- 规则层：`iptables -C` / `ip6tables -C`（`_verify_rules`，不写任何东西）；
- 成员层：一次 `ipset save` 取真值（`_members`），与目标比差异；
- 不一致才重新下发（规则走 `_clear_*` / `_ensure_*`，成员走差量）。

**首次同步也读真值**：`_MEMBERS` 初始为空（未知），第一轮先 `ipset save`，
避免把上一进程留下的内核残留条目当成「已同步」。

**下发失败的重试节奏**：失败时仍记住形态，但把下一次重试拉长到
`RULE_RETRY_INTERVAL = 60` 秒（由审计探测发现缺口后重新下发），
避免「一次失败就每 10 秒重放一遍全部规则命令」——那正是本次优化要消除的空转。

**失败可见**：不再 `2>/dev/null` 静默，子进程 stderr 按「命令族」限频记录
（`FAIL_LOG_INTERVAL = 600` 秒/族，行尾带被抑制的次数）。daemon 启动时通过
`firewall.set_logger(_log)` 把告警并入 `data/frpwaf.log`（接口缺失时静默跳过）。

**稳态效果**：名单与配置都不变时，`sync_from_store()` 一轮 **0 次 fork**
（仅 3 条 SQL + 纯内存比对），只有审计轮才会多一次 `ipset save` 与几条 `-C` 探测。

**记得调用 `invalidate()` 的场合**：`frpwaf_block` / 规则是**跨进程共享**的，
但记忆是**每进程私有**。宝塔插件端（`frpwaf_main.py`）与 daemon 各自持一份，
所以插件端在 `_fw_sync()` / `kernban_sync()` / 卸载 `teardown()` 前后都调
`firewall.invalidate()`：

```python
def invalidate():
    """作废本进程的同步记忆，强制下一次同步按内核真值重新对齐。"""
    with _sync_lock:
        _MEMBERS.clear()
        _RULES.update({"mode": None, "ports": (), "block_port": 0, "checked_at": 0.0})
        _sets_checked_at = 0.0
```

不调也不会丢数据（最多等一个 600 秒审计周期），但会出现「插件端刚解封、
另一进程还按旧记忆把条目写回内核」的窗口；调用后该窗口消失。
插件端用 `getattr` 探测 `invalidate`，兼容没有该函数的旧版 `firewall.py`。

## 5. 三种处置模式与关闭清理（重要）

内核层处置由两个开关决定（`_mode()`）：

| 模式 | 条件 | 内核动作 | 被封 IP 看到 |
|---|---|---|---|
| `drop` | `fw_sync_enabled` 开 | 下发 DROP，清理 REDIRECT | 连接超时，**无页面**（静默） |
| `redirect` | `fw_sync_enabled` 关 + `block_page_enabled` 开 | 摘除 DROP，下发 nat REDIRECT 到拦截页服务 | 封禁页 / 风控页 |
| `off` | 两者都关 | 清理 DROP 与 REDIRECT | 连接重置，无页面 |

> **为什么 redirect 模式必须先摘 DROP**：nat/PREROUTING 在 filter/INPUT 之前，
> 但改道后的包（目的端口变成 `block_page_port`）仍会在 INPUT 命中 `FRPWAF_BLOCK`
> 的 DROP 规则（源 IP 仍在集合中），从而「刚改道就被丢弃」。故 redirect 模式先
> `_clear_drop()` 再 `_ensure_redirect()`。

**教训（历史）**：把 `fw_sync_enabled` 关掉后，如果只停止「继续同步」而不清理已下发的
规则，内核里旧的 ipset 条目 / iptables 规则**仍在丢包**，表现为「面板显示已关闭内核封禁，
却仍被拦截」。因此所有路径统一调用 `sync_from_store()`，由它按模式决定
DROP / REDIRECT / 清理——不再有「关就 teardown」的分支：

- `daemon._fw_sync()`、`/api/config` 保存、`/api/kernban/sync`。
- 插件端 `frpwaf_main._fw_sync()` / `kernban_sync()`。
- 卸载：`uninstall_waf()`、`uninstall.sh` 仍调用 `teardown()` 彻底拆除。

`teardown()` 删除 INPUT 跳转、清空并删除 `FRPWAF_BLOCK` 链、删除 nat `FRPWAF_REDIRECT`
链、销毁两个 ipset。

### 5.1 REDIRECT 目标端口（`_redirect_ports`）

- 显式配置 `block_page_redirect_ports`（逗号分隔，如 `"80,8080"`）优先；
- 留空则自动读取 frps 配置的 `vhostHTTPPort`（`frp.load_config("frps")`）；
- 都取不到 → 退化为 DROP（至少保证拦截）。

规则幂等：先 `iptables -t nat -C` 判存在，不存在才 `-A`。IPv6 走 `ip6tables -t nat`。
拦截页服务本身见 `app/blockpage.py` 与 [04 §3.7.1](04-数据模型与配置项.md)。

## 6. 后台对账与解封

- `daemon._bg_loop()` 每 **30 秒**（`_BG_INTERVAL`，历史为 10 秒）调一次 `_fw_sync()`，
  把当前名单/封禁**对账**到内核；即使某次同步失败，下个周期会自愈
  （另有每进程 600 秒的规则/成员审计兼底，见 §4.5）。
  周期放慢的前提是：firewall 已改为状态记忆化（稳态 0 fork），
  实时封禁由事件驱动路径覆盖，30 秒仅做底部轮询。
- 代价：临时封禁的**释放粒度**从 10 秒变粗为 30 秒（集合自身的 per-entry timeout
  仍按时生效，实际“多活”最多 30 秒，可接受）。
- 解封：`/api/bans` 的 `unban` 会先 `store.unban_ip()` 再 `firewall.remove(ip)`
  再 `_fw_sync()`，立即从内核移除。
- 封禁到期：后台 `engine.auto_release()` 释放，下一次 `_fw_sync()` 时集合中
  已到期的临时条目也会因 `timeout` 归零由 ipset 自行移除。

## 7. 状态查询（`status()`）

返回：

```json
{
  "available": true,          // 是否支持（root + ipset + iptables）
  "enabled": true,            // 处置模式 != off
  "mode": "drop",             // drop / redirect / off
  "set4": 4,                  // frpwaf_block 条目数
  "set6": 0,                  // frpwaf_block6 条目数
  "rule": true,               // INPUT 是否已挂 FRPWAF_BLOCK
  "redirect": false,          // nat/PREROUTING 是否已挂 FRPWAF_REDIRECT
  "redirect_ports": [18080]   // 当前 REDIRECT 目标端口
}
```

> `status()` 填 `available/mode/enabled/set4/set6/rule/redirect/redirect_ports`；
> `/api/kernban` 与插件端 `kernban_status` 仍会覆盖 `enabled` 为当前 `fw_sync_enabled`
> （表示「内核丢包封禁」开关本身），并在 UI 上结合 `mode` 展示实际处置。

在宝塔插件端「**IP 名单 / 封禁**」页的「内核级封禁」卡片（含状态与「立即同步」按钮）
可手动触发 `kernban_sync`；独立 Web 端自 2026-10 起也提供「**内核封禁**」页
（状态 + 「立即同步」，二次确认 + 审计）。也可直接调用 `/api/kernban/sync`。

### 7.1 其它工具函数

| 函数 | 作用 |
|---|---|
| `remove(ip)` | 从内核集合移除单个 IP/CIDR（解封时调用；`ipset del -exist`），并同步移除记忆 |
| `invalidate()` | **作废本进程的同步记忆**，强制下次同步按内核真值重新对齐（多进程场景用，见 §4.5） |
| `flush()` | 清空集合内所有条目（**保留**集合与 iptables 规则），并作废成员记忆 |
| `teardown()` | 删除 iptables 规则/链与两个 ipset（卸载时调用），并作废全部记忆 |
| `set_logger(fn)` | 注入日志函数，让防火墙告警并入 `data/frpwaf.log`（可选） |
| `status()` | 状态查询（见 §7），新增回调/监听地址无关字段不变 |

> `flush()` 与 `teardown()` 的区别：前者只清条目（规则仍在，集合仍在），
> 后者彻底拆除（下次 `sync` 会重新 `_ensure()` 建好）。关闭 `fw_sync_enabled` 走
> **`teardown()`**（彻底拆除，避免残留规则继续丢包）。

### 7.2 谁在调用同步

| 调用方 | 时机 |
|---|---|
| `daemon._bg_loop()` | 每 **30 秒**对账一次（底部自愈） |
| `daemon` `/api/config`、`/api/kernban/sync` | 策略保存 / 手动同步 |
| `daemon` `/api/bans`、`/api/iplist` | 封禁/解封/名单变更后立即触发（异步合并，不阻塞响应） |
| `engine` 第 5/6 步命中封禁 | 触发一次异步同步（事件去重，同一时刻只跑一个） |
| 插件端 `frpwaf_main._fw_sync()` / `kernban_sync()` / `uninstall_waf()` | 插件页操作与手动同步；前后都 `invalidate()` |

## 8. 常见问题

| 现象 | 原因 / 处置 |
|---|---|
| `available=false` | 非 root / 缺 ipset 或 iptables。装 `ipset`、用 root 运行守护进程 |
| 关闭内核封禁后仍被拦 | 旧版本未清理残留；升级到含 Bug A 修复的版本，或手动 `kernban_sync`（关闭态会清理） |
| 被封 IP 看不到拦截页 | 检查 `block_page_enabled` 是否开、`block_page_port` 是否监听、`block_page_redirect_ports`/frps `vhostHTTPPort` 是否正确；HTTPS(TLS) 端口无法展示可读页面（退化为 DROP） |
| 白名单 IP 连不上 | 升级到含 Bug C 修复的版本（CIDR 差集）；确认白名单开关已开 |
| 内核集合条目数对不上 | 正常：白名单差集会拆分 CIDR；每 30 秒对账 + 每 600 秒审计 |
| 临时封禁延长后仍提前解封 | 旧版 `ipset add -exist` 不刷新 timeout；升级到含 §4.5 修复的版本（到期时刻变化超 10%/5 秒即重建条目） |
| 内核规则被外部清掉后很久才恢复 | 预期：记忆化后靠 600 秒审计发现；需立即恢复时点面板「立即同步」（会先 `invalidate()`） |
| IPv6 未生效 | 需系统有 `ip6tables`；`frpwaf_block6` 才创建 |
