# 11 · 开发运维与常见问题

## 1. 服务控制

服务可以由 **systemd unit**（`/etc/systemd/system/frpwaf.service`）或 **init 脚本**
（`/etc/init.d/frpwaf`）托管，`/usr/bin/frpwaf` 是后者的**副本**（供任意 PATH 下直接执行）。
两种方式都由 `frpwaf` 命令统一入口（systemd 托管时自动转调 systemctl）：

```bash
frpwaf start      # 启动（init.d：nohup python -m app.daemon；systemd：systemctl start）
frpwaf stop       # 停止（先 TERM，最多等 10s，再 KILL -9）
frpwaf restart    # 重启
frpwaf status     # 状态
```

- 启动命令：`cd /opt/frpwaf && nohup <python> -m app.daemon >> data/frpwaf.log 2>&1 &`
- Python：`/www/server/panel/pyenv/bin/python`，缺失时回退 `python3`。
- PID 文件：`/opt/frpwaf/data/frpwaf.pid`（**只有 init.d 路径靠它判定存活**；systemd
  用 `Type=simple`，主进程 PID 就是守护进程 PID）。
- **存活判定不再只看 `kill -0`**：还要 `/proc/<pid>/cmdline` 含 `-m app.daemon`，
  掉电/OOM 后 PID 被别的进程复用不会误判「已在运行」；`start` 会对「进程在但回调端口
  不通」自主回收重启，`stop` 能召回 pidfile 丢失的孤儿进程。详见
  [02 §3.1](02-目录结构与安装部署.md) 与 [12 Bug S](12-Bug修复记录.md)。

> **⚠️ 严禁使用 `pkill` / `pkill -f`** 杀进程！本项目守护进程是
> `python -m app.daemon`，`pkill -f "app.daemon"` 会误杀匹配到的**生产进程**
> （曾因此造成生产 WAF 被误杀的事故）。**只按精确 PID 终止**，或直接用
> `frpwaf stop`。

|---|---|---|
| WAF 运行日志 | `data/frpwaf.log` | 启动/停止/拒绝连接/登录/心跳/后台异常；>2MB 截断保留尾部 1MB |

## 3. 备份与恢复

### 3.1 自动快照备份（`data/backup/`，P2-3.11）

守护进程（`app/daemon.py` 的 `_bg_backup`）**每 24 小时**把数据库快照一份到
`/opt/frpwaf/data/backup/`，**保留最近 7 份**（`store.BACKUP_KEEP`）。这是
本机自动的「时间点回退」机制，不靠外部定时任务。

| 项 | 值 |
|---|---|
| 备份文件 | `data/backup/frpwaf-YYYYMMDD-HHMMSS-ffffff.db`（本地时区，**微秒定宽**） |
| 周期 | 24 小时（`_BG_BACKUP_EVERY`） |
| 保留份数 | 7（一天一份 ≈ 一周；裁剪按**文件名排序**，字典序 = 时间序） |
| 失败重试 | 600 秒后重试（`_BG_BACKUP_RETRY`），**不**像成功那样排到 24 小时后 |
| 权限 | `0600`（与 `frpwaf.db` 一致，含全量审计日志/名单） |
| 磁盘门槛 | 目标分区剩余 **< 200MB 直接跳过本次**（`BACKUP_MIN_FREE`） |

**周期是按「磁盘上最新一份备份的 mtime」算的**，不是只看进程内计时：

- 服务重启**不会**把 24 小时重新数一遍（不会因为频繁重启就永不备份）；
- 反过来，**停机超过 24 小时后启动，第一轮后台循环（≤ 30 秒内）就会立刻补一份**，
  不需要等到下一个周期；
- 后台循环首轮固定检查一次（`next_backup = 0`），由 `_bg_backup` 自己判定是否真该做。

实现要点（运维需要知道的就三条）：

1. **热备**，用 SQLite 官方 `Connection.backup()`（页级备份协议），WAL 模式下与并发写
   天然安全——备份期间回调继续写入，快照仍是一致的，**不需要停服务**；
2. **不持全局写锁**（独立连接），几十 MB 的备份不会把回调请求堵死；
3. **先写 `.db.tmp` 再 `os.replace` 原子落地**：备份到一半被杀不会留下半个 `.db`，
   且临时文件不以 `.db` 结尾（不会被当成一份可用备份）；中断残留的 `.db.tmp`
   超过 1 小时会被自动清理（`_clean_stale_tmp`）。

> **裁剪只认本程序的命名**：只有 `frpwaf-<时间戳>.db` 形态的文件会被当成备份参与
> 「保留 7 份」的裁剪。你手工 `cp` 进 `data/backup/` 的 `manual-2026.db`、`keep-me.txt`
> **永远不会被自动删掉**（旧版秒精度命名 `frpwaf-YYYYMMDD-HHMMSS.db` 仍会被识别，
> 且因名字最小被优先裁掉）。

### 3.2 手工恢复（运维最常用）

从自动备份回滚到某个时间点，**顺序不能变**：

```bash
# 1) 先停服务：不停服务替换文件无效（daemon 仍持有旧连接，写进的是被替换掉的旧 inode）
frpwaf stop          # 或 systemctl stop frpwaf / /etc/init.d/frpwaf stop

# 2) 看一眼有哪些备份（名字即时间，越靠后越新）
ls -l /opt/frpwaf/data/backup/

# 3) 关键一步：删掉旧的 -wal / -shm！
#    残留的 frpwaf.db-wal 属于「旧库」，启动时会被回放进刚恢复的库 → 数据库损坏。
rm -f /opt/frpwaf/data/frpwaf.db-wal /opt/frpwaf/data/frpwaf.db-shm

# 4) 把选定的备份拷成正式的库（先把当前坏库留个痕，别直接盖掉）
cp -a /opt/frpwaf/data/frpwaf.db /root/frpwaf.db.broken.$(date +%F-%H%M%S)
cp -a /opt/frpwaf/data/backup/frpwaf-20261122-075216-123456.db /opt/frpwaf/data/frpwaf.db
chmod 600 /opt/frpwaf/data/frpwaf.db

# 5) 起服务并确认
frpwaf start && tail -f /opt/frpwaf/data/frpwaf.log
```

> 恢复后**不必**手工跑内核同步：daemon 启动后后台循环首轮就会调
> `firewall.sync_from_store()`，内核集合会按恢复后的名单重新对齐（白名单差集不变）。

### 3.3 磁盘守卫与失败观测

- 剩余空间低于 **200MB** 时**跳过**本次备份（而不是写个半残文件），日志里有一条
  「磁盘剩余空间不足（剩余 XMB，低于阈值 200MB），已跳过备份」；
- 每次失败（含跳过）都会让 **`/api/metrics` 的 `db_backup_fail` 计数 +1**（纯内存，重启清零）：

```bash
# 看备份失败次数（需先登录拿 cookie，见 docs/10 §四）
curl -s -b /tmp/c.txt http://127.0.0.1:7080/api/metrics | grep -o '"db_backup_fail":[0-9]*'
```

> 「备份一直在失败」= 「误删/误清理后没有回退点」，属于必须处理的告警，
> 不要当成日志噪声。空间不足就清日志（`purge_logs`）或扩容，处理后下一轮自动恢复。

### 3.4 备份**不包含**什么（容易误以为「恢复备份 = 恢复一切」）

| 不在 `data/backup/*.db` 里 | 说明 |
|---|---|
| **`data/frpwaf.json`（配置）** | 开关/窗口/阈值/账号/密钥全在这里，**单独一个文件**。恢复备份**不会**恢复配置；配置要单独拷（见 3.5） |
| `data/frpwaf.log` | 运行日志 |
| `data/GeoLite2-City.mmdb` | 归属地库（可选件，丢了只影响归属地显示） |
| `data/frp_backup/`、`data/upgrade_backup/` | frp / 在线升级各自的备份目录 |

> 所以完整的「换机迁移/回滚」= **库快照（`data/backup/*.db`）+ 配置（`frpwaf.json`）** 两样都要，
> 只拿库会得到一个「名单封禁都在、但策略全回默认」的半血实例。

导出接口给的是另一个东西：`GET /api/export` 导出**名单 + 封禁历史 + 配置（机密掩码）**
的 JSON，适合人工查阅/跨机搬名单，**不是**数据库备份，也不能直接当库恢复（见 [10 §13.2](10-HTTP_API参考.md)）。

### 3.5 手工备份（不依赖自动快照）

- **数据备份**：直接复制 `/opt/frpwaf/data/`（`frpwaf.db` + `frpwaf.json`）。
  建议先 `store.checkpoint(truncate=True)` 或停服务，保证 WAL 已合并。
- **配置备份**：`frpwaf.json` 单独保存即可（含名单之外的策略/账号/密钥）。
- **frp 备份**：升级前 `frp.py` 自动备份到 `data/frp_backup/<kind>-<时间戳>/`，
  可 `frp_rollback` 还原。
- **恢复**：停服务 → 覆盖 `data/` → 启动（细节见 3.2，别忘了 `-wal`/`-shm`）。

## 4. 私有包加载机制（开发必读）

插件后端在**宝塔面板常驻进程**里运行，不能用通用包名 `app` 导入运行代码
（会与面板自身/其它插件的 `app` 包冲突）。本项目用私有包名 **`frpwaf_app`**：

- `_app_pkg_dir()`：优先 `/opt/frpwaf/app`，回退插件目录 `app/`，
  再回退 `../frpwaf/app`；都找不到抛**中文** `FileNotFoundError`。
- `_load_app_pkg()`：`importlib.util.spec_from_file_location(_APP_PKG, __init__.py,
  submodule_search_locations=[pkg_dir])` 注册私有包；被顶替时重建。
- `_app(modname)`：比对 `app/*.py` 的 **mtime 签名**，源码变更时**丢弃旧包重新导入**
  （面板常驻，否则一直跑旧代码）。

> 开发时改了 `app/*.py`，插件端会在下次调用时自动重载；但**守护进程**是独立进程，
> 需 `frpwaf restart` 才生效。Web 端与插件端共享同一份代码目录。

> **运行层只留 `app/`、`web/`、`data/`**：面板载荷（`frpwaf_main.py`、`index.html`、
> `info.json`、`install.sh`、`uninstall.sh`、`frpwaf.init`、`frpwaf.service`）只在
> 插件目录里有一份，在线升级不会再写它们进 `/opt/frpwaf`（详见 [02 §4](02-目录结构与安装部署.md)）。
> 所以排查「哪份代码在跑」时不需要在两处对比 `app/`——两边都指向 `/opt/frpwaf/app`。

### 4.1 守护进程的后台线程

`daemon.main()` 启动三个后台线程：

1. **`_bg_loop()`**（每 30 秒一轮，`_BG_INTERVAL`）：
   - `engine.auto_release()` 释放到期封禁（记日志）；
   - `store.trim_logs()` / `store.trim_bans(20000)` / `store.trim_ai_review()` 裁剪日志与历史；
   - `_fw_sync()` 对账内核封禁（已记忆化，稳态一轮 0 次 fork）；
   - `blockpage.ensure()` 兜底拦截页配置；
   - 每约 60 秒（按秒计而非数轮）做一次 `checkpoint(truncate=True)` 回收 `-wal`；
   - 每约 10 分钟写一条心跳日志（含生效封禁数、内存占用）。
2. **`_snapshot_loop()`**（每 10 秒）：把突发观测快照写入 `data/burst_snapshot.json`
   （只序列化内存数据，无 DB、无 fork；与主轮询解耦，避免 30s 边界抖动被误判为 `stale`）。
3. **`ai.loop_forever()`**（每 20 秒醒一次）：到间隔则执行一次 AI 审查（见 [08](08-AI自动IP审查.md)）。

> 主轮询从 10s 放慢到 30s 的前提是内核同步已改为状态记忆化；
> 代价是临时封禁的释放粒度变粗为 30s（集合自身的 per-entry timeout 仍按时生效）。

> 两者都用 `daemon=True`（随主进程退出），异常均被捕获并记入 `frpwaf.log`，不会导致服务退出。

## 5. 打包发布

```bash
cd <仓库检出目录>          # 注意：生产机的 /opt/frpwaf 自 2026-11-28 起已无 build.sh
bash build.sh          # 仅组装 -> dist/frpwaf
bash build.sh zip      # 组装并打 zip -> dist/frpwaf.zip（可直接上传宝塔）
bash build.sh install  # 组装并安装到本机插件目录

# 开发机没有 zip 命令时（如 Windows Git Bash）用等价脚本：
python scripts/make_plugin_zip.py   # -> dist/frpwaf.zip
```

> **生产已改为纯发布包驱动**：`/opt/frpwaf` 只留 `app/`、`web/`、`data/`，
> 发布侧文件（`build.sh`/`docs/`/`tests/`/`README.md`）与面板载荷
> （`frpwaf_main.py`/`index.html`/`info.json`/`install.sh`/`uninstall.sh`/`frpwaf.init`/`frpwaf.service`）
> 都已移出。原因是在线升级会把发布包里的这些文件覆盖到 `/opt`（那份没人在读），
> 而 `build.sh` 又依赖这些文件才能组包，两者互斥。现行流程见 [02 §2.0](02-目录结构与安装部署.md)。

- 插件包**根目录 = 仓库根目录**（`app/ web/ info.json install.sh ...` 直接在内），
  zip 也以**包内文件为顶层**（不含 `frpwaf/` 外壳），宝塔上传即可识别。
- 打包会清理 `__pycache__`/`*.pyc`/`.DS_Store`。
- **发布需用户明确同意**，且须先改版本号（见 [13-变更历史与版本.md](13-变更历史与版本.md)）。

## 6. 调试技巧

### 6.1 起一个隔离实例（不动生产）

用独立的 `FRPWAF_HOME` 与端口起临时实例，避免影响生产：

```bash
export FRPWAF_HOME=/tmp/frpwaf_test
mkdir -p "$FRPWAF_HOME/data"
# 写一份独立配置，改用非默认端口（避免与生产的 7080/7082/7081 冲突）
# 注意：面板、回调、拦截页三个监听**都要**错开，否则会与生产实例抢端口
cat > "$FRPWAF_HOME/data/frpwaf.json" <<'JSON'
{
  "http_addr": "127.0.0.1",
  "http_port": 17080,
  "frp_handler_addr": "127.0.0.1",
  "frp_handler_port": 17082,
  "block_page_port": 17081,
  "web_enabled": true,
  "admin_user": "admin",
  "admin_password": "frpwaf-local-test",
  "fw_sync_enabled": false
}
JSON
# 从项目目录启动（代码仍来自 /opt/frpwaf/app，数据写到 FRPWAF_HOME）
cd /opt/frpwaf
FRPWAF_HOME=/tmp/frpwaf_test /www/server/panel/pyenv/bin/python -m app.daemon &
echo "隔离实例 PID=$!"
# 访问 http://127.0.0.1:17080/  （账号 admin / 上面设的 frpwaf-local-test）
```

要点：

- `FRPWAF_HOME` 决定 `data/`（DB/配置/日志/PID）位置；**不设则默认 `/opt/frpwaf`**。
- 用非默认端口（如 17080 / 17082 / 17081）且 `http_addr` 设 `127.0.0.1`，避免与生产冲突/暴露。
  只改 `http_port` 不够：回调（`frp_handler_port`，默认 7082）与拦截页（`block_page_port`，
  默认 7081）会被生产实例占用，隔离实例的回调监听会启动失败（只告警不影响面板启动，
  日志里会有「回调独立监听启动失败」）。
- 配置里**别用 `admin_password: "123456"`**：那样 `password_changed` 会被推导为 `false`，
  登录后除概览/改密外的 API 全部 403，测接口很容易误判为「接口坏了」。
- 隔离实例默认 `fw_sync_enabled: false`，**不要**在生产机器上开内核封禁测试
  （会改写生产 ipset/iptables）。
- **关闭隔离实例时按精确 PID**：`kill $隔离实例PID`，**不要** `pkill`（会误杀生产）。

### 6.2 查看后台/调试信息

本项目**没有** `FRPWAF_DEBUG` 之类的调试开关。调试主要靠：

- `data/frpwaf.log`：启动/停止/拒绝连接/登录/心跳/后台异常（`daemon._log()`）；
- 面板「运行日志」页（插件端 `get_log` / Web 端「运行日志」页 `GET /api/syslog`）；
- 前台直接跑 `python -m app.daemon`（不 nohup）可看到 stdout 的启动行
  与 `traceback.print_exc()` 打印的决策异常栈。

### 6.2.1 静态检查（pi-lens / Pyright）与噪声抑制

本项目**不使用类型提示**（见 `code-patterns` 技能 §1），且核心交互对象是动态对象：
宝塔面板传入的 `get` 参数对象、`maxminddb` 的 `Record`、手写 `toml_lite` 解析器、
`frp.load_config()` 的 `(ok, dict_or_msg)` 联合返回。Pyright 对上述代码的类型推断
**全部是误报**（运行时由 `ok` 标志 / 异常 / 可选依赖降级兜底）。

因此项目根新增两个配置，把“真问题”与“本技术栈固有噪声”分开：

| 文件 | 作用 |
|---|---|
| `pyrightconfig.json` | `typeCheckingMode: "off"`（Pyright 官方配置，LSP 与 CLI runner 都读）；保留语法/解析级诊断 |
| `.pi-lens.json` | `rules.*.disable`：按规则 ID 关闭本项目固有噪声（Pyright 类型规则、Semgrep 误报、JS 风格提示、Markdown 表格风格、ruff 现代化规则等） |

> **改动后需重启 pi 会话 + 清理 LSP 诊断缓存**：Pyright 的 LSP 服务在会话启动时加载配置，
> 运行中的会话不会重新读取；更关键的是 pi-lens 会把 LSP 诊断**落盘缓存**到
> `~/.pi-lens/projects/<项目哈希>/cache/lsp-workspace-diagnostics.json`，
> **重启后仍复用旧结果**（表现为“改了配置、重启了，噪声依旧”）。
>
> 清缓存（缓存可再生，安全）：
> ```bash
> rm -f ~/.pi-lens/projects/*/cache/lsp-workspace-diagnostics.json
> rm -f ~/.pi-lens/projects/*/cache/project-snapshot.json.gz
> ```
> 先验证配置本身生效（不依赖缓存）：
> `~/.pi-lens/tools/node_modules/.bin/pyright --outputjson` → `errorCount: 0`。
>
> 需要恢复严格类型检查时：删掉 `pyrightconfig.json`（或改回 `"basic"`）、
> 从 `.pi-lens.json` 移除 `project-stack-noise` 组，清缓存后重启会话。

### 6.2.2 公开仓库镜像（过滤 AI 端资产）

本项目内网仓库（Gitea）包含 AI 端资产（`.claude/`、`.agents/`、`.codex/`、`.pi/`、`scripts/`、
`AGENTS.md`、`CLAUDE.md` 等）。推送到**公开仓库**（GitHub）时这些不应外泄，
但 `.gitignore` **无效** —— 它们**已被 git 跟踪**，而推送到另一远端发送的是同一批 commit 对象。

正确做法是**过滤历史后推送到另一个克隆**：

```bash
node scripts/make-public-mirror.cjs [输出目录]   # 默认 <仓库同级>/frpwaf-public
```

脚本行为（**只在独立克隆上操作，不碰当前仓库与 origin**）：

1. `git clone --no-hardlinks <本仓库> <输出目录>`；
2. `git filter-branch --index-filter 'git rm -r --cached --ignore-unmatch <排除项>' --prune-empty --tag-name-filter cat -- --all`；
3. 清理 `refs/original` + `gc`；
4. 校验：HEAD 与抽样提交内无排除项残留（有则退出码 1）；
5. 打印规模对比、镜像顶层内容与推送命令。

**排除清单**（见脚本常量 `EXCLUDES`）：`.agents`、`.claude`、`.codex`、`.pi`、`scripts`、
`AGENTS.md`、`CLAUDE.md`、`docs/agent-migration.md`、`docs/tasks`、`.pi-lens.json`。

注意事项：

- 过滤后提交哈希与内网仓库**不同**（历史被重写），属预期；每次同步重跑脚本即可。
- `--prune-empty` 会合并“只动了被排除路径”的空提交，因此镜像提交数**少于**原仓库。
- 若公开仓库已有旧历史，更新需 `git push --force` —— **属危险操作，须用户明确授权**。
- 该脚本自身位于 `scripts/`，**不会**进入公开镜像。

### 6.3 模拟 frps 回调

```bash
# 回调默认走独立监听 127.0.0.1:7082（frp_handler_port）；端口改过时按配置替换
curl -s -X POST 'http://127.0.0.1:7082/frp/handler?op=NewUserConn' \
  -H 'Content-Type: application/json' \
  -d '{"content":{"remote_addr":"1.2.3.4:5555","proxy_name":"web","proxy_type":"tcp","user":{"user":""}}}'
# 放行: {"reject": false, "unchange": true}
# 拒绝: {"reject": true, "reject_reason": "blacklist"}
```

> 注意：`/frp/handler` 仅接受**本机来源**（127.0.0.1/::1）。从其它机器/容器网络
> 模拟回调会得到 `403 forbidden`（属预期防护），需在 WAF 所在主机上执行；
> 非本机拒绝次数可在 `/api/overview` 的 `frp_remote_denied` 字段查看。
>
> 回调专用监听（`127.0.0.1:7082`）**只接 `/frp/handler`**，其它路径一律 404；
> 面板监听（`7080`）仍然兼容 `/frp/handler`（所以旧 `frps.toml` 也能工作），
> 只是不享受独立并发配额。若回调监听启动失败（端口被占），服务仍会启动，
> 日志会有「回调独立监听启动失败」，此时回调退回面板监听兼任。

### 6.5 异步任务（提交 + 轮询）与进度排查（P2-3.5）

在线升级（`/api/upgrade/apply`）与 AI 连接测试（`/api/ai/test`）是**长耗时**操作：
升级要下载几十 MB、覆盖几百个文件再重启；模型调用上限 120s。以前它们跑在**请求线程**里，
而宝塔面板的 Nginx 默认 **60s 超时**先到——浏览器弹「失败」，后台其实已经成功
（升级场景用户会反复点、重复覆盖同一批文件；AI 场景会并发打模型，既烧额度又看不出真实结果）。

现在两者都改成 **「提交 + 轮询」**（实现：`app/job.py`）：

| 项 | 值 |
|---|---|
| 状态文件 | `data/job_upgrade.json`、`data/job_ai_test.json`（一个 `kind` 一个文件，权限 `600`） |
| 写入方式 | 临时文件 + `os.replace` 原子替换（不会读到半截 JSON） |
| 心跳间隔 | 10 秒（`job.HEARTBEAT`） |
| 僵死阈值 | 60 秒（`job.STALE`，约 6 个心跳） |
| 串行 | 同一 `kind` 同时只允许一个任务；僵死任务不占名额 |
| 保留 | 状态文件**不自动删除**，任务结束后留在磁盘上（下次提交覆盖）；`job.clear()` 仅测试/排障用 |

**排障最实用的一条**：状态就是一个 JSON 文件，直接 `cat` 就能看当前进度 / 上次结果：

```bash
cat /opt/frpwaf/data/job_upgrade.json    # 升级跑到哪一步、上次成功还是失败
cat /opt/frpwaf/data/job_ai_test.json    # 最近一次模型调用的结果
```

字段含义（`job_id` / `kind` / `running` / `percent` / `msg` / `done` / `ok` / `error` /
`ts` / `started` / `finished` / `ms`）见 [10 §12.1](10-HTTP_API参考.md)。

**为什么卡住也不会永远转圈**：后台执行线程每 10 秒刷一次 `ts`。若面板重启或线程被打断，
`running=true` 而 `ts` 超过 60 秒未更新，任何一次状态读取都会把它改写成「已结束 + `ok:false`」，
`msg` 为「任务状态已中断（服务可能重启过），请刷新页面确认最终结果」。
所以看到这句话**不等于失败**——升级末尾本来就包含重启，请刷新页面看版本号与
`data/frpwaf.log` 确认最终结果，不要因为这句话就又点一次升级。

**跨进程可读，无需 IPC**：状态文件在 `data/` 下，插件端与守护进程读的是**同一份**
（`FRPWAF_HOME` 相同时，默认都是 `/opt/frpwaf`）。所以从宝塔插件页提交的任务，
Web 端也能看到进度，反之亦然；不需要它们互相通信，也没有额外的 socket/端口。

> 两点实现边界（已知，不影响日常使用）：
> ① **串行是按进程的**：进程内读写共用一把锁；跨进程靠「提交前先读状态文件」判断，
> 两端同时提交存在极小的竞态窗口，此时最终状态以**最后写入者**为准（原子写保证文件不坏）；
> ② 写入方是**提交任务的那个进程**（插件端提交时是面板进程写，Web 端提交时是守护进程写）。
> 所以看进度时**优先看 `status` 接口返回的值**，而不是凭“应该哪个进程在写”判断。

## 7. 常见问题（FAQ）

### Q1：面板打不开 / 登录后又跳回登录页

- 检查服务：`frpwaf status`；端口：`ss -lntp | grep 7080`。
- **先确认监听地址**：面板默认只绑 `127.0.0.1`，从外网访问不到是**预期行为**。
  用 `ss -lntp | grep 7080` 看是 `127.0.0.1:7080` 还是 `0.0.0.0:7080`；
  需要远程访问时在网页端「设置 → 监听与安全」勾选「允许远程访问」（或手改
  `data/frpwaf.json` 的 `http_addr` 后重启），并自行确认云安全组已放行。
- **登录后被弹回改密页**：说明 `password_changed=false`（默认口令未改），
  按提示改密即可；改密会轮换会话密钥，需用新口令重新登录（属预期）。
- 若经 HTTPS 反代，设 `X-Forwarded-Proto: https` 或 `cookie_secure=true`
  （否则 Cookie 因 `Secure` 标记不被回传——本项默认不加，见 [09](09-认证与安全.md)）。

### Q2：点击插件报 `FileNotFoundError: .../app/__init__.py`

插件包结构不对（缺少 `app/` 或**多套了一层文件夹**）。重新用 `bash build.sh zip`
生成 `dist/frpwaf.zip` 上传安装；确认压缩包**根目录**直接含 `app/`。

### Q3：frp「安装/升级」报 `ModuleNotFoundError: app.frp`

旧版本 bug。当前版本已用私有包名 `frpwaf_app` 加载修复（提交 `b8628fb`）。

### Q4：关闭了内核封禁，为什么还被拦？

旧版本关闭开关时未清理内核残留。当前版本任何关闭路径都会 `teardown()`
（Bug A，提交 `cedf595`）。若仍有残留：在插件端「IP 名单 / 封禁」页的内核封禁卡片点一次手动同步（关闭态会清理），
或手动 `iptables -D INPUT -j FRPWAF_BLOCK; ipset destroy frpwaf_block`。

### Q5：白名单 IP 却连不上

黑名单是**大段 CIDR**、白名单是其中**小 IP** 时的差集问题（Bug C）。升级到含
`_apply_whitelist` 的版本。确认「白名单」开关已开。

### Q6：改了 `frps.toml` 后 frps 起不来

新版 frp 严格解析，旧字段会 `unknown field`。用插件端「frp 管理 → 配置」保存
（自动 `verify` + 失败回滚），或升级时 `_migrate_config` 自动迁移。

### Q7：连接日志按「动作」筛选查不到数据

宝塔路由的 `action=a` 会污染 `get.action`。前端须用 **`log_action`** 参数
（代理筛选用 **`log_proxy`**）。已在代码与前端规避。

### Q8：卸载后 frps 全线拒绝连接

卸载时若未先移除 `frps.toml` 的 `[[httpPlugins]]`，frps 会一直回调已停止的 WAF
（fail-closed）。本项目 `uninstall_waf()` / `uninstall.sh` 已按「先移除回调再停 WAF」
处理。手动修复：删掉 `frps.toml` 中 `name="frpwaf"` 的块并重启 frps。

### Q9：内核封禁显示 `available=false`

需 root + 系统安装 `ipset`、`iptables`。Debian：`apt install ipset iptables`。

### Q10：归属地显示「未知」

未找到 GeoLite2 库或未装 `maxminddb`。`app/geo.py` 按顺序探测以下路径（取第一个存在的）：
`/www/server/panel/config/GeoLite2-City.mmdb`（宝塔自带）→
`/usr/share/GeoIP/GeoLite2-City.mmdb` → `data/GeoLite2-City.mmdb`。
把 mmdb 放到任一位置即可；纯离线、无网络请求。

### Q11：运行日志刷 `ConnectionResetError` traceback（已修复）

**现象**：`data/frpwaf.log` 反复出现

```
Exception occurred during processing of request from ('45.79.211.97', 58032)
... ConnectionResetError: [Errno 104] Connection reset by peer
```

**根因**：扫描器/客户端连上 7080 端口后**半途断开**（请求行还没发完就 RST），
`http.server` 的默认 `handle_error` 会把该异常完整堆栈打印到 **stderr**；
而服务脚本以 `nohup ... >>frpwaf.log 2>&1` 启动，stderr 与 stdout 合并写入运行日志。

**修复**（Bug I，`app/daemon.py`）：重写服务器 `handle_error`，
`ConnectionResetError` / `BrokenPipeError` / `TimeoutError` 等客户端断连类异常**静默**，
每 10 分钟最多汇总一行「已静默 N 条客户端断连异常」；其余异常仍打印完整堆栈。
**判读**：日志中偶尔出现该汇总行属正常（说明有人在扫 7080），无需处理；
若不再出现任何汇总行也正常（无人扫）。

### Q12：frps 日志刷 `no route found`（frp 自身行为，非 Bug）

**现象**：`/var/log/frps.log` 反复出现

```
[W] [httputil/reverseproxy.go:500] do http proxy request [host: book.nightb.cn] error: no route found: book.nightb.cn /32_32299/24.html
[W] [httputil/reverseproxy.go:500] do http proxy request [host: 47.106.172.12:80] error: no route found: 47.106.172.12 /
```

**含义**：该日志由 **frp 服务端二进制**产生（`pkg/util/vhost` 的 `CreateConnection`），
不是本插件打的。`host` 是请求携带的域名/地址，第二段是请求路径与路由用户。
出现它说明：**有人直接访问了 frps 的 HTTP 代理端口（`vhostHTTPPort`），
但其 Host 不匹配任何已注册的 http 代理域名** —— 常见于：

- 扫描器直接扫 IP:端口（`47.106.172.12 /`）；
- 探测未配置的域名（`book.nightb.cn /32_32299/24.html`）；
- 攻击者构造的路径扫描。

frp 对这类请求**返回 404 页面并记录一条 Warn**，属预期防御行为，**不影响正常业务**。

**判读与处置**（按推荐顺序）：

1. **可忽略**：日志量不大时可不管——它恰好说明 frp 正常拒绝了未知 Host。
2. **降低记录级别**：插件端「frp 管理 → 配置修改」把 `log.level` 改为 `error`
   （保存后重启 frps 生效）。注意这会同时隐藏其它 `[W]` 警告（如隧道连接失败提示）。
3. **不开无用监听**：若根本没用 HTTP 代理（无 `vhostHTTPPort` 需求），
   在 frps 配置中清空 `vhostHTTPPort` 并重启 frps，该端口不再监听，日志自然消失。
4. **限制来源**：`vhostHTTPPort` 仅应被 CDN/反代访问时，用系统防火墙限制来源 IP
   （插件端「frp 管理 → 一键放行端口」只负责放行，收紧需手动加防火墙规则）。

> ⚠️ 注意：HTTP 代理（vhost）**不会触发 `NewUserConn` 回调**（frp 的该钩子只覆盖
> `tcp`/`stcp`/`https`/`tcpmux`），因此这类扫描流量**不经过本 WAF 的决策与审计**。
> 若需要拦截它们，应在上游 CDN/反代或系统防火墙层处理，或改用 tcp 代理类型。

### Q13：站点整站 522 / CDN 回源失败（AI 误封边缘 IP）

**现象**：源站部署在 CDN（Cloudflare 等）之后，浏览器大量 `522`，静态资源
（`*.css` / `*.js` / `site-manifest.json` / `logo.svg`）全部加载失败。

**根因**：CDN 边缘节点 IP 为全站访客回源，天然「单 IP 高频」；AI 审查
（尤其 `ai_min_conns` 调低后）将其判为恶意并**永久拉黑**，CDN 回源连接被拒 →
边缘节点无法取到源站内容 → 522。

**处置**：

1. **一键恢复**：插件端或 Web 端「IP 名单 / 封禁」页点「解封全部黑名单」
   与「解封全部临时封禁」（二次确认，立即刷新内核规则）；
2. **确认保护开启**：AI 审查页「CDN 回源保护」（`ai_cdn_guard`）应为开——
   判定为 CDN 回源的 IP 只记录不封禁；
3. **预防**：源站位于 CDN 之后时，IP 级自动封禁应交给 CDN 自身
   （Cloudflare WAF 等）；本 WAF 的 `remote_addr` 只是边缘节点，无法代表真实访客。

详见 [08 §5.2.1](08-AI自动IP审查.md) 与 [12 Bug M](12-Bug修复记录.md)。
