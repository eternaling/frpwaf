# 03 · 工作原理与准入决策

## 1. 为什么用 frp `httpPlugins`

frps 原生**没有**「按来源 IP 拒绝连接」的能力。frp 从 0.53 起提供
**`httpPlugins`**（服务端插件）机制：frps 在关键事件发生时，向配置的 HTTP
地址 POST 一个 JSON 请求，插件返回是否拒绝。

本项目只用到其中一个事件：**`NewUserConn`**——每当有**新用户连接**进入 frps
时触发。这样即可对「访问代理端口的来源 IP」做准入控制。

注入到 `frps.toml` 的配置块（由插件后端 `apply_to_frps` 写入）：

```toml
[[httpPlugins]]
name = "frpwaf"
addr = "127.0.0.1:7080"
path = "/frp/handler"
ops = ["NewUserConn"]
```

> `addr` 指向 WAF 守护进程；`path` 固定 `/frp/handler`；`ops` 只订阅 `NewUserConn`。
> 端口若在面板改过（`set_web_port`），这里会同步更新。

## 2. 回调协议（frps ⇄ WAF）

frps 发起：

```
POST http://127.0.0.1:7080/frp/handler?version=0.1.0&op=NewUserConn
Content-Type: application/json

{
  "version": "0.1.0",
  "op": "NewUserConn",
  "content": {
    "remote_addr": "1.2.3.4:54321",
    "proxy_name": "web",
    "proxy_type": "tcp",
    "user": { "user": "alice", "metas": {...}, "run_id": "..." }
  }
}
```

WAF 返回：
- **放行**：`{"reject": false, "unchange": true}`
- **拒绝**：`{"reject": true, "reject_reason": "blacklist"}`

`daemon._frp_handler()` 解析：
- `content.remote_addr` → `_split_addr()` 拆出 IP 与端口（兼容 IPv6 `[::1]:port`）。
- `content.proxy_name` / `content.proxy_type` / `content.user.user`。
- 调 `engine.decide()` 得 `(allow, reason)`。
- 写 `conn_log`（action = `allow`/`reject`，reason 记录命中规则）并 `bump_proxy`。
- 返回上面对应的 JSON。

> 除 `NewUserConn` 外的其它 op（`Login`/`NewWorkConn`/`CloseProxy`/`Ping`）一律
> 返回放行，不做处理。

> **回调覆盖范围（重要）**：frp 的 `NewUserConn` 仅对 **tcp / stcp / https / tcpmux**
> 类型代理触发；**http 类型代理不触发该回调**（frp 官方实现如此）。因此纯 http 代理
> 的访问不经过本 WAF 决策链（CC 检测等均不生效），其防护应以基础自动封禁、
> 限速或前置反向代理手段为主。

> **回调来源校验**：`/frp/handler` 仅接受**本机来源**（127.0.0.1 / ::1 / ::ffff:127.0.0.1）；
> 其它来源直接 403（并计入 `frp_remote_denied` 概览计数），防止任意可达 7080 的来源
> 伪造 `remote_addr` 触发封禁。

## 3. fail-closed：可用性优先的取舍

frp 对 `httpPlugins` 是 **fail-closed**：**只要 `frps.toml` 里还留着回调配置，
而 WAF 不可达（进程挂了 / 端口不通），frps 会拒绝所有用户连接。**

这是一把双刃剑：
- **好处**：WAF 异常时默认「全拒」，不会出现「防护失效却无人察觉」。
- **代价**：WAF 一挂，业务即中断。

因此有两条重要约定（详见 [14-运维注意事项与约束.md](14-运维注意事项与约束.md)）：

1. **停用/卸载顺序**：先移除 `frps.toml` 的回调配置并重启 frps，再停 WAF。
   否则 frps 会一直回调已停止的 WAF → 全线拒绝。
   代码在 `uninstall_waf()`、`uninstall.sh` 中已按此顺序处理。
2. **决策异常时放行**：`daemon` 里 `engine.decide()` 抛异常时 `allow=True`
   （reason=`engine-error`）。这是**有意**的——WAF 内部逻辑错误不应导致 frp 全线拒绝；
   真正的「WAF 进程不可达」由 frps 的 fail-closed 兜底。

> 换言之：**进程级不可达 → frps 全拒（fail-closed）；单次决策异常 → 放行（fail-open）。**
> 前者保证「防护在」，后者保证「小 bug 不炸业务」。

## 4. 决策顺序（`engine.decide`）

按**优先级从高到低**：

| 顺序 | 条件 | 结果 | reason |
|---|---|---|---|
| 0 | IP 非法（无法解析） | 放行 | `invalid-ip-pass` |
| 1 | 白名单开关开 且 命中白名单 | **放行** | `whitelist` |
| 2 | 黑名单开关开 且 命中黑名单 | **拒绝** | `blacklist` |
| 3 | 命中生效中的封禁（`ban_log` 未过期） | **拒绝** | `banned` |
| 4 | 限速开关开 且 该 IP 每秒新连接超限 | **拒绝** | `rate_limit` |
| 5 | 自动封禁开关开 且 窗口内连接数 ≥ 阈值 | **拒绝**（并写入 `ban_log`） | `auto_ban` |
| 6 | 攻击类型封禁开关开 且 命中对应特征 | **拒绝**（并封禁） | `auto_ban_cc` / `auto_ban_scan` / `auto_ban_ssh` |
| 7 | 代理级冷却开关开 且 该代理冷却中 且 该 IP 为新出现 | **拒绝** | `proxy_cool` |
| 8 | 其余 | **放行** | `""` |

要点：

- **白名单优先**：即使同时命中黑名单，白名单先命中即放行。
- **白名单保护自动封禁**：`whitelist_enabled` 开启时，白名单命中的 IP 在第 1 步即
  直接放行（`return`），因此第 5、6 步天然不会收到白名单 IP——自动封禁受白名单保护，
  不会误封管理员自己的 IP（与 AI 审查的跳过策略一致）。
- **开关独立**：`blacklist_enabled` / `whitelist_enabled` 各自独立生效。
  关掉黑名单开关后，黑名单**不参与**判定（应用层放行），内核同步也会同步剔除
  （见 [05-内核级封禁.md](05-内核级封禁.md)）。
- **自动封禁**：判定命中后会调用 `store.add_ban()` 写入一条带到期时间的封禁，
  之后该 IP 在封禁期内由「顺序 3」直接拒绝。**默认关闭**，因为 frp 的 HTTP/HTTPS
  代理天然有大量并发连接，阈值过低会误封正常用户（见下）。
- **限速**：内存计数（`engine._rl`），实现细节见下。

### 攻击类型自动封禁（第 6 步，三类独立开关，默认全部开启）

在既有「连接数阈值」自动封禁之外，按攻击特征提供三个独立开关
（配置项见 [04](04-数据模型与配置项.md) §3.4.1），检测全部在**内存**中完成
（窗口计数，不查库、无磁盘 IO），命中阈值后才写封禁记录。
三个开关**默认开启**（用户要求开箱即用）：阈值偏保守，且 CC/扫描用可自愈的
临时封禁兜底误伤；不需要的类型可在设置页单独关闭。

| 类型 | 检测依据 | 处置档位 | reason |
|---|---|---|---|
| CC 攻击（`auto_ban_cc_enabled`） | 同 IP 窗口内对 **https/tcpmux 代理**的新建连接数 ≥ 阈值（frp 对 **http 类型代理不触发 NewUserConn 回调**，故纯 http 代理不参与 CC 检测，其高频访问由基础自动封禁/限速覆盖） | **临时封禁**（可自愈，防误伤正常高峰） | `auto_ban_cc` |
| 端口扫描（`auto_ban_scan_enabled`） | 同 IP 窗口内访问的**不同代理数** ≥ 阈值 | **临时封禁**（可自愈） | `auto_ban_scan` |
| 敏感服务爆破（`auto_ban_ssh_enabled`） | 同 IP 窗口内命中敏感服务代理（**仅非 HTTP 类**）的连接数 ≥ 阈值 | **永久黑名单**（正常用户不会高频新建此类连接；黑名单开关关闭时降级为临时封禁） | `auto_ban_ssh` |

- 敏感服务关键字按**非字母数字边界**匹配（`ssh_22`、`mysql-db`、`mongodb`、
  `postgresql`、`elasticsearch` 命中；`wordpress`、`cardpay` 这类含 `rdp` 子串的
  普通代理名**不会**误判）：`ssh`、`mysql`、`redis`、`rdp`、`mongo`、`postgres`、
  `elastic`、`telnet`、`smb`、`vnc`、`ftp`。
- 命中封禁后该 IP 的窗口计数在锁内**只认领一次**（计数型阈值封顶，扫描型记录认领状态）——并发连接中
  只有一个线程能触发封禁写入（不会重复写库），也避免「封禁写入可见前的窄窗口内
  并发连接再次累积、二次触发」；手动解封后同一窗口内不会凭旧计数立即再次触发，
  窗口过期自动重置。
- 写库失败时计数型回退一格、扫描型清除认领状态，下一次连接可重试写入。
- 窗口过期自动重置（惰性重置，无后台线程）。
- 计数结构有界（每类上限 5000 IP，超限先清过期再淘汰最旧），与 `_rate_limited` 的策略一致。
- 计数语义：**含本次连接**，且仅在开关开启期间累积（开启前的历史连接不计入）。
  第 5 步（基础自动封禁）与第 6 步共用同一套内存计数与原子认领机制，
  决策路径**不做任何数据库查询/磁盘 IO**。

### 突发观测与代理级冷却（第 7 步，默认关闭）

针对「海量不同 IP × 每 IP 仅 1 次」的分布式爬虫/扫描（单 IP 维度检测
按设计不触发），按**代理维度**观测与处置：

- **突发观测（A，始终开启、纯内存、无副作用）**：`engine._burst` 按代理名聚合
  窗口（`burst_window`，默认 60s）内的连接数、独立 IP 数、每 IP 仅 1 次占比、
  代理类型；后台每 10s 生成快照，面板「突发观测」卡片展示并自动定性：
  - `distributed_probe`（疑似分布式探测）：独立 IP ≥ 50 且仅 1 次占比 ≥ 80%；
  - `single_source`（单点高频）：连接数 ≥ 100 且独立 IP ≤ 3；
  - 其余为 `normal`。
  内存有界：最多 50 个代理、每代理 2000 个 IP，超出后不再收录新 IP（`truncated` 标记）。
- **跨进程可见性**：观测/冷却状态在守护进程内存中，宝塔插件端运行在面板进程
  （两个独立进程，内存互不可见）。守护进程后台每 10s 将快照原子落盘
  `data/burst_snapshot.json`（含 `ts` 与运行时生效配置），插件端
  `burst_status` 读取该文件；超过 30s 未更新（守护进程未运行）时返回上次数据并
  标记 `stale`，面板显示过期提示。Web 面板直连守护进程 `/api/burst`，读实时内存。
- **冷却拦截（C，`proxy_cool_enabled`，默认关闭）**：后台每 10s 判定，某代理在窗口内
  同时满足「连接数 ≥ `proxy_cool_min_conns`、独立 IP ≥ `proxy_cool_uniq_threshold`、
  仅 1 次占比 ≥ `proxy_cool_single_pct`」时进入冷却 `proxy_cool_seconds`（最小 10s）；
  冷却期内该代理**新出现 IP** 的首连被拒（reason `proxy_cool`），
  进入冷却时已见过的 IP（`known` 冻结集合）放行。
  `known` 取 **eligible 口径**：仅「首现时代理不在冷却中」的 IP 有冻结资格，
  防止「爆发—停歇—再爆发」循环中上一轮被拒 IP 在重入冷却时被洗白；
  冷却条目有硬上限（100，超限按进入时间淘汰最旧）。
  冷却期内累计连接数达下限会**续期**（覆盖观测窗口滚动场景）；条件消失后到期自然失效。
- **误伤面**：仅凭连接层行为无法区分「恶意爬虫」与「出口 IP 变化的真实用户」
  （移动网络切换、动态 IP、CDN 回源）。因此默认关闭，建议先用突发观测确认流量
  性质、可接受偶发误伤后再启用；白名单 IP 不受影响（第 1 步直接放行）。
- 决策路径仅做 O(1) 内存查询（`_cool_active` / `_cool_blocks`），判定遍历
  （O(代理 IP 数)）在后台线程完成，不违反「决策路径禁止磁盘 IO/全表扫描」红线。

### 限速（`_rate_limited`）
- 计数结构：`ip -> (窗口起点, 计数)`，**固定 1 秒窗口**（与 `rate_limit_per_sec` 无关）。
- 逻辑：若距上次窗口起点已 ≥1 秒，则重置计数；每次调用 `cnt += 1`；
  `cnt > per_sec` 即判定超限 → 拒绝（reason `rate_limit`）。
- `rate_limit_per_sec <= 0` 或 `rate_limit_enabled=false` 时**不生效**。
- 有界增长：当 `_rl` 条目 > 5000 时，先清理窗口起点超过 2 秒的旧项；
  仍超限则淘汰最旧条目，保证突发不同 IP 时也不越界。
- 注意：这是「**每秒新连接数**」的粗粒度限速，且仅针对 `NewUserConn` 事件计数。

### 缓存与失效

- **名单缓存**（`engine._cache`）：TTL 3 秒。管理端增删名单后调
  `engine.invalidate_cache()` 立即失效，改完即生效。
- **封禁缓存**（`store._bans`）：TTL 2 秒。增删封禁后调 `store.invalidate_bans()`。
- **配置缓存**（`config._cache`）：TTL 1 秒，写盘后 `invalidate()`。
- 这三层短缓存让**连接热路径**几乎不读盘，同时保证管理操作「秒级生效」。

## 5. 自动封禁为什么默认关闭

frp 代理端口（尤其 `vhostHTTPPort`/`vhostHTTPSPort`）会承接来自大量终端
（浏览器、App、爬虫、CDN 回源）的连接，短时间内同一来源 IP 产生几十上百次
连接是**正常**现象。若自动封禁阈值设得过低，会把正常用户/回源节点误封。

因此：
- `auto_ban_enabled` 默认 **`False`**；
- 默认阈值 `auto_ban_threshold=200`（60 秒窗口）也偏保守；
- 面板设置页提示「自动封禁默认关闭，请确认阈值合理后再开启」。

> **攻击类型自动封禁（第 6 步）是例外：三个开关默认开启。**
> 这是所有者明确要求「开箱即用、不需要手动设置」的结果，与第 5 步的
> 保守策略不冲突：第 6 步的默认阈值足够高（CC 300 次/60s、扫描 20 个
> 不同代理/60s、敏感服务 20 次/60s），且误伤代价由处置档位兜底——
> CC/扫描为**临时封禁可自愈**，敏感服务爆破才走永久黑名单（正常用户
> 不会高频新建 ssh/mysql 类连接）。升级后如发现误封，可在设置页把对应
> 阈值调高或直接关闭该类型开关；参数留 0 会被视为「未设置」并自动回退
> 默认值（见 [04 §3.4.1](04-数据模型与配置项.md)），关闭开关才是停用方式。
>
> 需要「按来源 IP 的连接数阈值自动封禁」时，仍推荐优先使用 **AI 审查**
> （带归属地与行为上下文，误伤更小），或先观察连接日志再定阈值。

## 6. 一次连接的完整数据流

```
1. 用户 → frps 代理端口
2. frps → POST /frp/handler?op=NewUserConn
3. daemon._frp_handler 解析 remote_addr/proxy_name/proxy_type/user
4. engine.decide(ip, port, proxy_name, proxy_type, user)
     ├─ 白名单?  → allow
     ├─ 黑名单?  → reject
     ├─ 封禁中?  → reject（之后记一次突发观测）
     ├─ 限速超?  → reject
     ├─ 自动封禁触发? → add_ban + reject
     ├─ 攻击类型命中?（CC/扫描→临时封禁；敏感服务→永久黑名单）+ reject
     ├─ 代理级冷却中且新 IP? → reject（proxy_cool，默认关闭）
     └─ 否则     → allow
5. store.add_log(...)  +  store.bump_proxy(...)
6. 返回 {"reject": false|true, ...}
7. 后台线程每 10s：engine.cool_check()（冷却进入/续期/清理）
   + firewall.sync_from_store() 把黑名单+封禁下发 ipset/iptables
   → 被禁 IP 的包在内核层 DROP，连接计数停止增长
```

## 7. 与内核封禁的关系

应用层拒绝（返回 `reject:true`）**只影响本次连接**：TCP 握手已经完成，frps
断开连接后，攻击者可以立刻重连，每次重连都会记一条 `conn_log`、消耗一次决策。

`firewall` 模块把「黑名单 + 生效封禁」同步到 ipset，并在 INPUT 链首用一条规则
DROP 命中集合的来源，使被禁 IP 的包**在内核层就被丢弃**，从根本上止住连接。
详见 [05-内核级封禁.md](05-内核级封禁.md)。
